## 2. Transação e bloqueios

### Migration 1 (RBAC)
- `CREATE TABLE`, `CREATE POLICY`, `DROP POLICY`, `ALTER FUNCTION` — PostgreSQL DDL autocommit em migrations Supabase
- Nenhum `BEGIN/COMMIT` necessário — cada statement é atômico por si
- Risco baixo: reversível via DROP

### Migration 2 (RLS produto_imagem)
- `CREATE POLICY` — atomicidade por statement
- `ALTER TABLE produto_imagem ENABLE ROW LEVEL SECURITY` — irreversível sem DROP de policies
- Risco baixo

### Migration 3 (Unique principal)
**Contém `BEGIN/COMMIT` explícito:**
```sql
BEGIN;
LOCK TABLE produto_imagem IN SHARE ROW EXCLUSIVE MODE;
UPDATE produto_imagem ... (data cleanup);
CREATE UNIQUE INDEX ...;
COMMIT;
```

**Atenção:** O Supabase CLI (`supabase db push`) aplica migrations como **um script SQL** enviado ao servidor. O `BEGIN/COMMIT` dentro do script é tratado normalmente pelo Postgres. O `LOCK TABLE` pode bloquear por milissegundos (14 rows). Risco muito baixo.

**Se usar `supabase db push --dry-run`:** o output mostrará o script completo. Verificar que o `BEGIN/COMMIT` está intacto.

### Recomendação
Aplicar migration 3 em horário de baixa atividade. O `LOCK TABLE` é breve, mas bloqueia writes concorrentes.

## 4. Roteiro de rollback

### Se aplicar migrations 1, 2, 3 (rollback individual)

#### Migration 3 rollback (imagem principal):
```sql
-- Remover RPC
DROP FUNCTION IF EXISTS public.produto_imagem_definir_principal(bigint, bigint);

-- Remover índice
DROP INDEX IF EXISTS produto_imagem_principal_unica;
```

#### Migration 2 rollback (RLS produto_imagem):
```sql
-- Remover policies novas
DROP POLICY IF EXISTS "produto_imagem_read_anon" ON produto_imagem;
DROP POLICY IF EXISTS "produto_imagem_read_authenticated" ON produto_imagem;
DROP POLICY IF EXISTS "produto_imagem_insert_admin" ON produto_imagem;
DROP POLICY IF EXISTS "produto_imagem_update_admin" ON produto_imagem;
DROP POLICY IF EXISTS "produto_imagem_delete_admin" ON produto_imagem;
DROP POLICY IF EXISTS "produto_imagem_read_admin_all" ON produto_imagem;

-- Remover policy adicional em produto
DROP POLICY IF EXISTS "produto_read_active_authenticated" ON produto;

-- Restaurar policies originais (funciona apenas se admin_user existir)
CREATE POLICY "produto_imagem_read_admin" ON produto_imagem FOR SELECT TO authenticated USING (is_admin());
CREATE POLICY "produto_imagem_write_admin" ON produto_imagem FOR ALL TO authenticated USING (is_admin());
```

#### Migration 1 rollback (RBAC + Storage):
```sql
-- Remover admin_user e trigger
DROP TRIGGER IF EXISTS admin_user_no_last_admin ON admin_user;
DROP FUNCTION IF EXISTS admin_user_prevent_last_delete();
DROP TABLE IF EXISTS admin_user CASCADE;

-- Restaurar is_admin() original (vulnerável — usar apenas em emergência)
CREATE OR REPLACE FUNCTION is_admin() RETURNS boolean AS $$
  SELECT EXISTS (SELECT 1 FROM auth.users u WHERE u.id = auth.uid() AND u.raw_user_meta_data->>'role' = 'admin');
$$ LANGUAGE sql SECURITY DEFINER STABLE;

-- Restaurar storage policies amplas (temporário — apenas emergência)
DROP POLICY IF EXISTS "product_images_insert_admin" ON storage.objects;
DROP POLICY IF EXISTS "product_images_update_admin" ON storage.objects;
DROP POLICY IF EXISTS "product_images_delete_admin" ON storage.objects;
CREATE POLICY "Authenticated upload" ON storage.objects FOR INSERT TO authenticated WITH CHECK (bucket_id = 'product-images');
CREATE POLICY "Authenticated update" ON storage.objects FOR UPDATE TO authenticated USING (bucket_id = 'product-images');
CREATE POLICY "Authenticated delete" ON storage.objects FOR DELETE TO authenticated USING (bucket_id = 'product-images');
```

> ⚠️ **Atenção:** Rollback da migration 1 restaura `is_admin()` vulnerável. Apenas em caso de emergência. Aplicar imediatamente a re-migração corrigida após.

### Recomendação de backup
